# Head-to-head benchmarks: wasm-spatial-core vs alternatives

Head-to-head, reproducible comparison of **LAS point cloud → Cesium 3D Tiles**
(the headline task) across engines that can plausibly attempt it.

The published result page is generated at `benchmarks/index.md` (served on
GitHub Pages). This directory holds the harness that produces it.

## Engines compared

| Engine | Role in this benchmark |
|--------|------------------------|
| **wasm-spatial-core** | Full pipeline: `parsePointCloudAuto → generateTileset` (octree + pnts encode) |
| **py3dtiles** (Python CLI, v12) | Full pipeline: `py3dtiles convert` (reference Python implementation) |
| **loaders.gl** | Parse-only — documents that it has **no LAS→pnts writer** (capability gap) |
| Cesium ion | Not timed — it is a cloud tiling service (upload + token), a different category. See the architecture table in the generated page. |

## Fairness controls

These are the credibility core. Every claim below is enforced by the harness:

- **Same input bytes.** All engines consume the identical file; SHA-256 (first 12 hex) is recorded per result.
- **Same no-op transform.** No reprojection on either side — we compare the raw-coordinate pipeline.
- **Same output target.** Both wasm-spatial-core and py3dtiles emit `.pnts` + `tileset.json`; output bytes and tile count are reported.
- **Trimmed mean.** 5 timed runs after 1 warmup, min/max dropped.
- **Honesty floor.** Rows where wasm-spatial-core loses or ties are kept. loaders.gl's inability to generate pnts is published as a finding, not hidden. The wasm RSS being higher than py3dtiles in some runs is shown as-is.

## Run it

```bash
# From repo root.
wasm-pack build --target nodejs --release --out-dir pkg-node -- --features point-cloud

# Python env for py3dtiles (it needs laspy for LAS support).
python3 -m venv bench/head-to-head/.venv
bench/head-to-head/.venv/bin/pip install "py3dtiles[las]"

# Optional: loaders.gl (its ESM deps can be flaky; the runner degrades gracefully).
npm install @loaders.gl/las

# Run each engine → JSONL.
WASM_PKG_DIR=pkg-node node bench/head-to-head/run-wasm.mjs bench/head-to-head/fixtures/canonical_500k.las > bench/head-to-head/results-wasm.jsonl
PATH="bench/head-to-head/.venv/bin:$PATH" python3 bench/head-to-head/run-py3dtiles.py bench/head-to-head/fixtures/canonical_500k.las > bench/head-to-head/results-py3dtiles.jsonl
node bench/head-to-head/run-loaders-gl.mjs bench/head-to-head/fixtures/canonical_500k.las > bench/head-to-head/results-loaders-gl.jsonl

# Aggregate → benchmarks/index.md + benchmarks/results.json
node bench/head-to-head/aggregate.mjs
```

CI runs all of this on push to `master` and publishes `benchmarks/` to GitHub Pages (see the `head-to-head-bench` job in `.github/workflows/ci.yml`).

## Files

| File | Purpose |
|------|---------|
| `shared.mjs` | Fairness helpers: timer (trimmed mean), RSS, result schema, pkg resolution |
| `run-wasm.mjs` | wasm-spatial-core runner (parse + tileset, per-stage timing) |
| `run-py3dtiles.py` | py3dtiles runner (`py3dtiles convert`, child RSS via getrusage) |
| `run-loaders-gl.mjs` | loaders.gl runner (parse-only; documents the no-pnts-writer gap) |
| `aggregate.mjs` | Reads `results-*.jsonl` → `benchmarks/index.md` + `benchmarks/results.json` |
| `fixtures/canonical_500k.las` | Spec-compliant 500k-point LAS (generated by laspy, the reference impl) |

## Why a separate canonical fixture?

The repo's historical `test-data/large/synthetic_500k.las` was generated by a
buggy writer that placed the point count at byte offset 100 (the VLR-count
field) instead of the ASPRS-specified offset 107. Standard tools (laspy,
py3dtiles, PDAL) could not read it. That bug has been fixed (see commit
`d424cf1`) and the in-repo fixtures regenerated, but the benchmark uses a
laspy-generated canonical file as the common input so the comparison is
provably fair against reference implementations.
